# 2026-10-05 第五轮：重启后的真实回归，抓出一个「串流时报警空闲」的 bug

## 起因

Owner 电脑重启。这是本项目第一次在**真实使用场景**下回归，暴露了一个单元测试和反复自检
都发现不了的缺陷。

## 抓到的问题（最严重的一个）

第一次跑体检就报：

```
[Pass] port-vd  四个 VD 端口此刻都空闲
```

同一时刻的事实：

```
Get-NetTCPConnection | Where LocalPort -in 38810..38840
::            38810  ::   0  Bound        11120   ← VirtualDesktop.Streamer
::            38820  ::   0  Bound        11120
::            38830  ::   0  Bound        11120
::            38840  ::   0  Bound        11120
192.168.11.2  38810  40.89.161.236 38813  Established  11120
```

**串流正在进行，工具说端口空闲。** 两个叠加的错误：

1. 查询只带 `-State Listen`，而 Streamer 的常态是 **Bound**，看不到；
2. 用「试着绑一下」判断占用，端口被持有时绑定失败抛 `WSAEACCES`，
   既分不清是谁持有，又**扰动了自己要测的东西**。

还有一个隐性 bug：占用进程查询在 PowerShell 里用了单引号，`$($_.LocalPort)` 被原样输出，
于是每个占用者都落成「未知」——这就是重启前那次「4 个端口被监听（未知）」的真正原因。

## 修正与验证

`ObserveVdPortsAsync` 一次查询拿到 端口/状态/占用进程/对端，检测项按状态说话：
Established → 「PC 侧通道是通的」；Bound 且占用者是 VD → 正常待机；
Bound 但占用者不是 VD → 唯一的警告分支；什么都没有 → 去看 streamer-proc。

修正后本机实测：

```
[Pass] port-vd  4 个端口上有活动会话：38810、38820、38830、38840
        38810: 已建立会话 → 192.168.11.14:36081（占用 VirtualDesktop.Streamer）
```

`192.168.11.14` 就是开工第一天在 ARP 表里记下的那台随机 MAC 设备——
**此刻正在串流的头显**。这是修正之后才第一次看到工具说对。

细节见 `notes/2026-10-05-port-state-finding.md`。

## 这一轮还确认了两件事

1. **`nat-type` 状态自己变了**：Cone/Restricted → **Open**。说明服务正常启动后，
   Streamer 通过 UPnP 在路由器上映射了 38810——这正好印证调研里
   `AllowRemoteConnections=true` 时 `UPnPManager` 会建映射（`ConnectionManager.cs:240-243`）。
2. **历史 diff 在真实场景有用**：重启后第一次跑就报出 2 处变化，正是上面那两件。

## 没验证的（与上一轮相同）

- 头显侧 adb 三个分支（无设备；本轮头显在串流但没插 USB，所以 adb 仍看不到它）。
- 广播实发未抓包（Npcap 已装但需管理员）。
- `fw-restore-vd` 仍卡 UAC。
