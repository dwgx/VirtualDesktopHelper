# 2026-10-05 第六轮：修复动作的诚实性，以及一个真修好的残留会话

## 这一轮最重要的事：一条会「谎报成功」的修复

拿 `streamer-restart` 去清四个残留套接字，工具报「成功」，实际 PID 纹丝不动。查下来叠了三层：

1. **Streamer 是提权运行的**（由服务拉起），非提权进程 `Stop-Process` 直接 `Access is denied`；
2. **脚本用 `-ErrorAction SilentlyContinue` 把这个错误吞了**，退出码仍是 0 → 我据此报成功；
3. **`ProcessStartInfo.Verb = "runas"` 在 `UseShellExecute=false` 时是空操作** ——
   而我们需要重定向输出才能拿到 stdout，所以「提权」从来没真正发生过。

修法（`Fixes.ElevatedAsync`）：

- 提权改由**内层** `Start-Process -Verb RunAs -Wait` 发起；
- 内层脚本**把自己的成败写进临时文件**，外层读那个文件 —— 因为 `Start-Process` 不传递子进程退出码；
- 内层脚本写成临时 `.ps1` 用 `-File` 启动 —— 把命令塞进外层 `-Command` 字符串会把引号搅烂（第一版就是这么失败的）；
- 修复动作带**后置校验**：PID 必须真的变了才算成功，并轮询等待。

## 真修好了

```
修复前：4 个 Established 套接字，建立于 17:27，已存在 49 分钟
        对端 192.168.11.14 那四个端口全部关闭（我实测扫过）
修复：--apply streamer-restart
        → 提权等 UAC 约 98 秒
        → 结果：成功 — Streamer 已重启：PID 11120 → 36784
修复后：旧套接字全部消失；新套接字 19:16:20 由新进程创建
        38810 Established → 40.89.161.236:38816
        38820/30/40 Bound（待机）
        工具报：「1 个通道刚建立：38810」
```

**检测 → 归因 → 修复 → 校验 → 重新归类，整条链在真实故障上跑通了。**

## 顺带修掉的两个「工具说错话」

1. **残留 Established 套接字**：Windows 只有在对端发 FIN 或超时后才改状态。
   实测对端早已退出、套接字还挂了 45 分钟。现在按会话年龄判读：
   2 分钟内=刚建立，更久=残留（警告 + 给清理动作）。
2. **verdict 自相矛盾**：会话正通着却说「串流很可能起不来」。现在分「串流中」与「未串流」两套说法，
   且明确「下面的隐患不影响当前这一局」。

## UAC 等待的体验

实测这一等可以到 98 秒。修复动作现在带 `NeedsElevation` 标记，按钮状态写成
「执行中（会弹 UAC，请点「是」——本机实测这一等可能要 1 分半）」，
不再让用户以为工具卡死。
