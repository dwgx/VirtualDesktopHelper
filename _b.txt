feat: parameter toggles refuse a running Streamer and verify what they wrote

Two bugs in the one control that writes to the Streamer configuration from the UI.

1. No running-Streamer guard. The CLI already refuses, for a good reason: the Streamer keeps a ~2 s
   debounced save, so a write underneath it is overwritten moments later. The UI had no such check,
   so clicking the toggle while streaming reported success and the change silently reverted. It now
   refuses with the reason stated, matching the CLI.

2. No post-condition. State was set from the writer's return value, which is not the same claim as
   "the value on disk is now what you asked for". This project has already shipped two repairs that
   reported success while doing nothing. It now re-reads the file and reports the confirmed value, or
   says the read-back disagreed and that the backup was kept.

Also fixes the list order. OrderByDescending(ReadOnly) put the 18 parameters a user can change below
ninety-odd account blobs they cannot, in a 111-row list — and the default scroll position landed on
a wall of ciphertext. The top of the list is now AllowRemoteConnections, EncryptLocalTraffic and
ShowPairingRequests, each with its caution / needs-reconnect badges and a toggle button, verified on
screen.

Verified: build clean, gate passes, 34 checks, Streamer process guard condition confirmed true on
this machine. The write path itself is NOT runtime-verified here — exercising it needs the Streamer
stopped, which needs UAC.
