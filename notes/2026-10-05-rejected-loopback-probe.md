# 回环探测：试过，然后撤掉了

## 想做什么

`research/13-endpoints/02-discovery-protocol.md` 的候选检测项 **D3 disc-38850-loopback**：
向 `127.0.0.1:38850` 发一个 17 字节全 0 的哑包，**预期无回包**。

理由听起来很干净：协议规定只对已知的 ConnectionID 回包（`-.112.cs:343-355`，回复在 `:451`），
所以「沉默」是正常结果。这样能把「端口存在」和「发现处理器还活着」分开——
读端口表做不到这件事。

## 为什么撤掉

**1. 17 字节包在协议里不是无害的哑包。**

同一份调研的机制段写得很清楚：17 字节包是连接前的**单播预告包**，
Quest 在 `ConnectTo` 前把它发给上一次发现记下的地址；PC 侧命中该分支后
执行 `this.\u0002(); break;`，**关闭本次运行的 38850 监听**（`-.112.cs:354`）。

也就是说，往 38850 打这个包**有可能直接把头显发现通道关掉**。

**2. 本机实测侥幸没出事，但这不构成安全性。**

发包后立刻查：

```
:::38850 pid=41956
VirtualDesktop.Streamer pid=41956 start=10/05/2026 19:36:12
```

PID 与启动时间都没变，监听还在。**但这是运气，不是证据**——
我没有逐行确认那条分支的所有进入条件，也没有在头显在线时复现过。
用一个可能关掉用户发现通道的探测，去换一个「端口活着还是处理器活着」的区别，
不划算。

**3. 它还把整轮体检卡死了。**

加上探针后 `--selftest` 挂了 100 秒以上、直接被超时杀掉，`_lb.txt` 根本没生成。
撤回后同一命令 6.8 秒跑完、34 项齐全。**挂住的原因我没查出来**——
一个我没搞明白为什么会挂的探测，更不该进用户会运行的工具。

## 结论

**不要在用户的运行中的产品上，往它的私有协议端口发未经确认无害的包。**

想要同样的信息，用只读的办法：`udp-discovery` 现在已经能给出
「端口有没有绑 / 绑在哪个地址 / 由哪个 PID 持有 / 回环发包后是否有应答」之前的全部事实。
「处理器是否还活着」这一层，留到有管理员抓包权限时用 pktmon 被动观察，
不要用主动发包去换。
