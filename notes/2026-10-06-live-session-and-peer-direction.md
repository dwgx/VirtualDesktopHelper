# 一次真串流：怎么拿 Windows 自己验这个工具，别验反了

2026-10-06。头显连上，工具报串流中，第一次在真会话上验。

## 工具说的

    串流会话  串流中：4 个通道已建立（端口 38810、38820、38830、38840），对端 192.168.11.14:37455
    udp-discovery  串流中：到头显的通道已建立，Streamer 已释放发现端口（正常）
    session-stale  警告  4 个到头显的通道仍是已建立状态（最早建立于 2 分钟前）

## Windows 自己说的

    38810 -> 192.168.11.14:37455  Established
    38820 -> 192.168.11.14:40227  Established
    38830 -> 192.168.11.14:39715  Established
    38840 -> 192.168.11.14:38891  Established

全中。

## 差点报了个假缺陷

第一遍查法是按 `RemotePort -in 38810,38820,38830,38840` 过滤 Established，**返回 0**。看上去就是
「工具凭空编了一次串流」。

方向反了。**38810-40 是 Streamer 绑定的本地端口**，对端头显用的是它自己的临时端口（这次是
37455 / 40227 / 39715 / 38891）。按 RemotePort 过滤不是「更弱的检查」，是**在查另一件东西**，而那件
东西恰好不存在。

写下来是因为：**任何拿 Windows 交叉核对这个工具的人都会先写出那个错的查询**，然后得出一个假的
「工具在编」。判据是：**先看对端端口落在哪个区间，再决定按 LocalPort 还是 RemotePort 过滤。**

## 顺带定下来的两件事

- **session-stale 报警告是对的。** 它量的是「多久了」，不是「断没断」，它自己的文案就是这么写的：
  这不等于串流已经断了 —— Windows 只有在对端发 FIN 或 TCP 超时之后才改状态，所以一次跑了半小时的
  正常串流，和一次头显一小时前就退出、套接字还挂着的残留，在这一张表里长得一模一样。真串流正是
  这句文案要面对的场景。
- **udp-discovery 判通过也是对的。** 通道都建立了，Streamer 让出发现端口就是正常状态——这正是它现在
  说的那句话，而不是报一个异常。

## 仍然做不到的

`adb devices` 还是空的。**这一屏只有在头显开了无线调试（开发者选项 → 无线调试）或者插 USB-C 的情况
下才有内容。** 串流通了不等于 adb 通了，这两件事是分开的。
