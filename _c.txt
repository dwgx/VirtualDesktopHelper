fix: --set-param announced success before checking whether it succeeded

The command printed 已写入 <key> = <value>, the backup path and the rollback line first, and only
then looked at the writer's Success flag. A failed write therefore announced itself as a successful
one, and the user walked away believing the configuration had changed.

It now reports failure when the write fails, and otherwise re-reads the file and compares before
claiming success — the same post-condition the UI toggle and both repairs use, for the same reason:
this project has already shipped repairs that reported success while doing nothing. On a mismatch it
says what the file actually contains and that the backup was kept, and exits non-zero.

Exit codes verified on this machine: 8 Streamer running, 2 unknown key, 7 DPAPI key, 2 missing
value. The success branch is not runtime-verified here, because exercising it requires the Streamer
stopped, which requires UAC.
