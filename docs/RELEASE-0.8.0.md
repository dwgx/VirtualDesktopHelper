# VDHelper 0.8.0 —— 让人来审自己的结论（第二版）

0.7.0 之后 30 多个提交。这一版修掉的东西分两类：**0.7.0 自己带出来的一个严重缺陷**，
和**把验证变成闸门**。

## 一、先修 0.7.0 里那个会跟 Windows 对着干的错

**0.7.0 的报告标题会说「此刻没有已建立的 VD 通道」，而同一份报告的 `udp-discovery` 说通道已建立，
Windows 显示有 4 条。**

```
改前：串流会话：此刻没有已建立的 VD 通道（不是「串流中」）。
      12. udp-discovery  串流中：到头显的通道已建立（正常）
      Windows            38810/20/30/40 → 192.168.11.14  Established

改后：串流会话：4 个通道已建立（端口 38810、38820、38830、38840），对端 192.168.11.14:37455
```

**原因不是笔误**：`HealthChecks` 把 `_livePorts` 只从 `fresh` 子集写，而标题读它。
**「有没有」和「新不新」是两个问题，从同一个集合里取，必然在一个场景里说反。**

「已建立但很旧的会话」——**那恰恰是 `session-stale` 存在的理由**——于是标题说没有通道。
**它触发得最频繁的时刻，正是用户最可能打开报告的时刻。**

**两份审计都漏了**：它们都在读检测项，**没有一个在读检测项被渲染成的那份文档**。
是渲染出 HTML 之后逐行读才看见的。

## 二、两份自审的 13 处「说的比测的多」

派了两个只读审计 agent，问题只有一个：**用户能看到的文字，有没有断言这段代码没有建立的东西。**
挖出来的东西形状高度一致。

### 能写坏配置的

| 缺陷 | 之前 | 现在 |
|---|---|---|
| `PreferredCodec` 等 **4 个键** | 类型是 `int (enum …)`，`StartsWith("enum")` 为假 → **枚举表从未被调用** | `--set-param PreferredCodec 999` 写得进去，**而同一键的字符串 `"999"` 正确拒绝**。改为 `Contains("enum")` |
| `FoveaSize` 等 **10 个浮点键** | 范围写成 `UI 滑块 0.4–1.0`，左半段解析失败 → **整段范围检查被跳过** | `FoveaSize 999` 写得进去。改为取分隔符两侧的数字 token |

**用直接调用发布程序集的探针，对全部 111 行逐行验过，不是抽样：19 个用例，0 失败。**

### 说了不等于做到的

- **脱敏漏了两条控制台路径**——报告声称「不写任何 DPAPI 密文、令牌、账户条目」，
  `--adb`/`--deep`/`--apply` **一个字都没过**，而 adb shell 原始回包正是最容易带出这种东西的地方。
- **IPv6 套接字被写成「到公网的已建立连接」**。`fe80::` 是链路本地，**就在这根线上**。
- **GPU 温度分支没做掩码**，`0x0` 拼成空列表，输出「驱动报的降频原因：。」
- **`nat-type` 摘要说「这条双层 NAT 结论不成立」，下一行的指引照原样断言了它。**
- **`wifi-quality` 先说「数值自相矛盾」，两行后又说「你确实连的是拥挤的 2.4 GHz」。**
- **`net-loss` 吞掉一个目标 30% 的丢包**，却拿同一个网关当「本机链路没问题」的证据。
- **`lan-reach` 把 `Probe`（正在解析）写成「已过期」。**
- **`nic-powersave` 说「两者都读进证据了」，而其中一个字段 `Get-NetAdapterPowerManagement` 根本不返回。**

**还有一条是我自己的注释编造了证据**：位表注释说节流分支「已由真机验证，依据是 89% 负载和 100.8 W」。
全仓 grep，**100.8 W 不存在**；**89% 是另一次记录的频率比，被读成了占用率**。已改成真正在册的那次，
**错误保留可见而不是删掉**。

## 三、新增检测项：`usb-headset`

**之前 `grep VID_2833` / `USB` 全仓零命中**，所以「头显没接上这台电脑」和「接上了但没在串流」给出的是同一份报告。

而这正是**插上 USB-C 却不工作时，第一个该回答的问题**——**既不需要 adb，也不需要头显配合**。

四种结果，因为其中两种是不同的故障：

| | | |
|---|---|---|
| 认得出、状态 OK | **通过** | PC 侧枚举到了 |
| 认得出但状态异常 | **警告** | 线和口通，驱动或设备有问题 |
| `VID_0000&PID_0002` | **警告** | **枚举上了，但 Windows 在读到身份之前就失败了**——**线/口问题，重装软件没用** |
| 什么都没有 | **未知** | **这不是故障**。本工具主场景是 Wi-Fi，那时本来就不会插 USB |

**「没有」这一支故意判未知**：判成故障，只会训练人忽略它。

## 四、六道闸门

前五道里，**有两道今天抓到的是我，不是代码**：

| 闸门 | 抓到过什么 |
|---|---|
| 症状反漂移 | 新检测项不被任何症状类引用，按症状筛选时永远出不来 |
| 退出码契约 | README 承诺的退出码**此前无人核对**。只读清单**硬编码**，结构上到不了改状态的命令 |
| 报告自洽 | **就是上面那个标题缺陷**——文档自己跟自己核对 |
| 文档覆盖 | `docs/checks.md` 是生成的，此前漂移过三次，全靠人手发现 |
| 引证 | **抓到我往注释里写凭记忆的行号**，还抓到我拿 VD 反编译源码的引用格式去指本工具自己的代码 |
| issue 模板 | issue 模板曾缺 `body:`，整套指引从未生效 |

**CI 本身今天坏了两次**：先是一个无上限的 `Start-Process -Wait` 让整个 job 挂了一小时、
后面所有闸门静默跳过；然后我把 CI 文件截成 0 字节提交了一次，又叠了一层 BOM 让 YAML 根本不加载。
**两次都是静默的。**

## 五、界面

- 参数页的值列**原来会截掉那个默认值**（`（未设置 → 用默认值 tru…`），而「不改的话它会是什么」
  正是这个页存在的理由。现在是 `未设置（默认 true）`。
- **每行都标 `PC 侧` 或 `头显侧`**：111 行里 57 行落在头显，此前唯一的区分线索是**它没有切换按钮**。
- 第三屏两个探针**原本把同一段话说两遍**，占了半个面板。

## 六、已知未覆盖

- **头显侧代码路径一次都没在真机上跑过。** 串流通了（本机实测 4 个已建立通道与 Windows 逐条对上），
  **但 `adb devices` 仍为空——串流通不等于 adb 通。** 第三屏要开无线调试或插 USB-C 才有内容。
- `nat-type` 仍然**明确说「这一项没有测」**。社区里 `HMBSbige/NatTypeTester`（MIT，NuGet `Stun.Net`，
  `net10.0` 直接可消费）能补上这个缺口，**但接了工具就要开始向外发包**——所以没接，等着定。
- 补丁 APK 的行为仍**未经真机验证**。

## 安装

    tools\publish.ps1
    dist\v0.8.0\VdHelper.exe     直接双击用

单文件自包含，**约 134 MB**，不需要装 .NET。校验：

    SHA256  351fb9427c366555cc3cdec7dd968587c1cf8fcb0c9a7fbaf01d30eb4989677c  VdHelper.exe
    版本    0.8.0
    自检    退出码 3（有隐患）

**没有代码签名**，第一次运行 SmartScreen 会拦一次——**这是预期行为**。
先 `certutil -hashfile VdHelper.exe SHA256` 核对，对得上再点「更多信息」→「仍要运行」。
