# VDHelper 0.9.0 —— 让闸门来审作者

0.8.0 之后 10 个提交，外加发布当天修掉的一个文档生成缺陷。这一版的主题是**闸门与它的作者**：
新加的那道闸门第一轮抓到的就是作者本人；另有两道写了之后被真实数据推翻、没有上线。

## 一、第七道闸门：ADB 只读白名单

`tools/check-adb-readonly.py`。它只问一个问题：**adb 探针到底会跑哪些 shell 命令？**

答案必须逐条写在白名单里，新命令**只能被显式加进去**——加进去这个动作本身就是一次决定。

**为什么是白名单而不是黑名单**：`headset-grant` 合法地执行 `pm grant`，那是写操作，而且它就该是写。
黑名单要么把它误报，要么给它开一个例外——而例外第一次被扩大之后，就不再是例外了。

第一轮审计的结果是「基本是旧闻」：探针跑的 `pm list packages` / `settings get` / `dumpsys package` /
`getprop` / 读无线 MAC / `ip addr` / `ps` / `pidof`，本来就全是读。**没有任何一条是错的。**

然后是有意思的部分：**写完它的下一轮，它抓的是作者本人。** 第三屏新加的两个命令
（`dumpsys battery`、`dumpsys thermalservice`）在闸门进 CI 的第一轮就被拦下，
确认是读之后才进的名单。**这道闸门对着写它的人第一次生效。**

## 二、两道闸门：写了，被真实数据推翻，撤了

同一天里有两道自建闸门在真实数据面前垮掉，**都没有上线**：

- **栅栏奇偶检查**（三行就能写）：README 的代码栅栏被弄坏两次，而当时的检查看不见它，
  因为坏掉时那句话已经进了代码块。写完拿 `docs/` 里现成的文件一试——`docs/report-export.md`
  报「3 个围栏，奇数」。去看第 29 行：**那是故意写的行内示例，它就在讲围栏这件事。**
  换成开合状态机也不行：**在语法上，「正文里举例」和「忘写闭栅栏」是同一个 token**，
  没有任何解析方式能把它们分开而不引入新的误判。
- **`check-emphasis.py`**：同类形状——造了一个自己信不过的检查，差点当成保护。
  自己发现，删掉。最后上线的强调检查是收在 `check-symptom-map.ps1` 里的那一版，
  它只管「CommonMark 不会当成开标记的 `**`」，那一条有确切的判据。

**两次都是同一个决定：写了，跑真实数据，被推翻，撤掉。**
理由也同一条：**会误报的闸门比没有闸门更糟——它教人忽略红色。**

## 三、第三屏新增：电量与发热

`headset-deep` 多了第 4 项子判定（`A7 电量与发热`），读 `dumpsys battery` 与 `dumpsys thermalservice`。

这两项和 PC 侧完全无关，却长得像 PC 侧的问题：**头显低电会自动关机，而关机前后它不再广播发现包**，
表现是「十分钟前还好好的」。热到降频同理。

四种结论，因为两种失败不是一回事：

| 读数 | 结论 | 含义 |
|---|---|---|
| 解析不出 `level` | **未知** | **没测成，不是「电量正常」** |
| `health` 不是 Good | 警告 | 头显随时可能自己断电 |
| `level` ≤ 15% | 警告 | 低电自动关机，发现广播随之停 |
| 其余 | 通过 | 读数在证据里 |

没连头显时走到的是**未知**这一支——它必须说「没测到任何东西」，
否则面板在没人看过的头显上会读成「电量没问题」。

## 四、报告说清它带了什么：头显 adb 序列号

`--report` / `--report-html` 的第三屏输出**包含头显的 adb 序列号**。
它此前既不在内部键表里、也不在 DPAPI 脱敏范围内——**一个普通的证据键，从整条脱敏链路旁边走过去了。**

**保留，不脱敏**，这是有意的：`--serial` 是公开参数，「是哪一台头显」本身就是诊断信息。
缺的不是脱敏，是**说清楚**。现在两种报告格式都会点名这一行，并提示贴到公开场合前自行删掉；
依据（`quest-adb-dashboard` 的 Do Not Share 清单把真实序列号列为不可公开）也写在报告里。

真正的发现是不对称：这个项目花了一整天决定 DPAPI 密文与账户条目绝不能进输出，
**而一个平铺直叙的证据键绕过了全部。**

## 五、发布当天修掉的一个文档缺陷

`tools/export-docs-site.ps1` 从 `docs/checks.md` 读本机实测表，但它的状态列只认英文
`Unknown`——而 `export-checks.ps1` 写出去的是自检原样的 `未知`。

于是，**「未知」的行被整行丢掉**：站点上的表说「共 34 项」（这一轮变成 33），
而那次运行实际有 36 项；`usb-headset` 从上线起就没在站点上出现过，因为它在本机永远是「未知」。

修法是三行：状态列接受 `未知`、计数认识它、徽标映射到 `unknown` 样式。
0.9.0 的站点显示全部 36 项（通过 21 / 警告 11 / 阻断 1 / 未知 3）。

**被丢掉的恰好是「什么都没测到」的那几行**——一个把「未知」从表里抹掉的站点，
和这个项目一直在防的那种说谎是同一个方向。

## 七、已知未覆盖

- **头显侧代码路径仍然一次都没有在真机上跑过。** 电量与发热的三个实测分支同样
  `[未验证]`——它们需要一个连着 adb 的头显。已验的是：能编译、未知分支能渲染、两条命令在白名单里。
- `nat-type` 仍然**明说「这一项没有测」**；STUN 方案（`HMBSbige/NatTypeTester`，MIT）仍在等决定，
  没接——接了工具就开始向外发包。
- 发布时这台机器上**头显不在网络上**（`lan-reach` 阻断），自检退出码因此是 4。
  0/3/4 都是合法结论，这一条的原始输出在 `docs/checks.md` 里。

## 安装

    tools\publish.ps1
    dist\v0.9.0\VdHelper.exe     直接双击用

单文件自包含，**约 134 MB**，不需要装 .NET。校验：

    SHA256  9b54d9c0625c26b81a0554a19ef1c150f415dd535a470d2f8950f7746918fc81  VdHelper.exe
    版本    0.9.0
    自检    退出码 4（阻断——发布时头显不在网络上；0/3/4 都是合法结论）

**没有代码签名**，第一次运行 SmartScreen 会拦一次——**这是预期行为**。
先 `certutil -hashfile VdHelper.exe SHA256` 核对，对得上再点「更多信息」→「仍要运行」。
